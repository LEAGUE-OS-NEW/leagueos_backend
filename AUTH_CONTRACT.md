# Authentication and onboarding API contract

All paths below are relative to `/api/v1`. Responses use the envelope
`{"success": boolean, "message": string, "data"?: object, "errors"?: object}`.

## Registration and verification

`POST /auth/register/` requires `first_name`, `last_name`, `email`, `password`, and
`confirm_password`. `username` and `phone_number` are optional. The passwords must match.
An explicitly supplied username is preserved; an omitted or blank username is generated by the
backend. A supplied phone must be an international number and is stored as canonical E.164;
omitted, `null`, and blank phones are stored as `null`. The request is:

```json
{
  "first_name": "Ada",
  "last_name": "Lovelace",
  "email": "ada@example.com",
  "username": "ada_lovelace",
  "phone_number": "+256772123456",
  "password": "StrongPass123!",
  "confirm_password": "StrongPass123!"
}
```

Registration verification is email-only. A successful registration or resend response has the following shape. `expires_in` and `resend_available_in` are calculated from backend configuration and must not be hard-coded by clients:

```json
{
  "success": true,
  "message": "...",
  "data": {
    "verification_required": true,
    "verification_channel": "EMAIL",
    "destination": "a**@example.com",
    "expires_in": 600,
    "resend_available_in": 120
  }
}
```

`POST /auth/verify-otp/` accepts `{"email": "ada@example.com", "otp": "123456"}`.
`POST /auth/resend-otp/` accepts `{"email": "ada@example.com"}`. Successful verification
returns the authenticated response below, including both tokens.

## Authenticated response

Login, successful OTP verification, refresh, and `GET /auth/me/` place user context at exactly
`data.user`. Login and verification also include `data.access` and `data.refresh`; refresh includes
the rotated tokens; `/auth/me/` includes neither token.

```json
{
  "success": true,
  "message": "...",
  "data": {
    "access": "<JWT when issued>",
    "refresh": "<JWT when issued>",
    "user": {
      "id": "<UUID>",
      "username": "ada_lovelace",
      "email": "ada@example.com",
      "first_name": "Ada",
      "last_name": "Lovelace",
      "phone_number": "+256772123456",
      "is_verified": true,
      "roles": ["Fan"],
      "permissions": [],
      "dashboard_access": {
        "entitlements": [],
        "default_entitlement": null,
        "default_route": ""
      },
      "onboarding": {"completed": false, "current_step": "COUNTRY"}
    }
  }
}
```

`POST /auth/login/` accepts `{"identifier": "email-or-username", "password": "..."}`.
Matching is case-insensitive. Phone numbers are not login identifiers. The legacy `email` request
field remains accepted as a compatibility alias but is not the canonical contract.

`POST /auth/token/refresh/` accepts `{"refresh": "<JWT>"}`. Only tokens associated with an active
server-side session can rotate. Tokens issued before session tracking was deployed have no such
record and require reauthentication. Rotation is single-use: one request succeeds and later or
concurrent reuse fails.

`POST /auth/logout/` requires bearer authentication and accepts `{"refresh": "<JWT>"}`. It
blacklists that refresh token and deactivates its session. `GET /auth/me/` requires bearer
authentication and returns the authenticated response shape above without tokens.

## Onboarding

Onboarding status contains saved preferences, `current_step`, and `completed`. Each selection
response contains the saved selection plus `current_step` and `completed`; skip also returns
`skipped_steps`. Completion and dashboard responses contain `configuration`, `current_step`, and
`completed`. Replaying an earlier step updates that saved preference but does not advance the
current step.
